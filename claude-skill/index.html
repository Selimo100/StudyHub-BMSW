Was es macht

Von einem Ordner voller Unterlagen zu einer fertigen Lernseite.

studyhub-summary ist ein Skill für Claude Code. Ein Skill ist eine gespeicherte Arbeitsanweisung: Statt jedes Mal aufs Neue zu erklären, wie eine gute Zusammenfassung aussehen soll, steht das einmal fest geschrieben da und wird mit einem Befehl abgerufen.

Du startest Claude Code im Ordner mit deinem Prüfungsmaterial und tippst /studyhub-summary. Danach passiert Folgendes:

Material lesen

Der Ordner wird rekursiv durchsucht und die relevanten Dateien werden tatsächlich gelesen — auch PDFs, nicht nur Dateinamen.

Lernziele abbilden

Jedes Lernziel wird auf Quellen, Konzepte, Beispiele und Übungen abgebildet. Fehlt Material, wird das vorher gemeldet.

Seite schreiben

Theorie, durchgerechnete Beispiele, typische Fehler, Übungen auf fünf Niveaus, vollständige Lösungen, Prüfungssimulation.

Einbinden

Die Seite landet am richtigen Ort im Repo und wird in der Fächerübersicht verlinkt. Die Suche findet sie automatisch.

Was es ausdrücklich nicht ist

Kein Spickzettel-Generator. Das Ziel ist eine Seite, mit der man den Stoff wirklich lernen kann — Lehrbuch, Übungsheft, Prüfungssimulator und Schlusscheckliste in einem. Typische Seiten sind entsprechend lang.

Voraussetzung: Claude Code muss auf deinem Rechner installiert und angemeldet sein. Das Skill selbst ist nur eine Sammlung von Textdateien — es funktioniert ohne Claude Code nicht.

Installation

Einmalig, dann steht der Befehl in jedem Projekt zur Verfügung.

  1. Repository klonen

    Falls du StudyHub noch nicht lokal hast:

    git clone git@github.com:Selimo100/StudyHub-BMSW.git ~/dev/school/StudyHub
  2. Skill ins persönliche Claude-Verzeichnis kopieren

    Persönliche Skills liegen unter ~/.claude/skills/ und gelten dadurch in allen Ordnern — nicht nur im Repo.

    mkdir -p ~/.claude/skills
cp -R ~/dev/school/StudyHub/claude-skill/studyhub-summary ~/.claude/skills/
  3. Konfiguration anlegen

    In config.md trägst du den Pfad zu deinem lokalen Repo ein. Die Datei ist bewusst nicht im Repo — sie enthält deine persönlichen Pfade.

    cd ~/.claude/skills/studyhub-summary
cp config.example.md config.md
  4. Zugriff aufs Repo erlauben

    Damit das Skill aus einem beliebigen Fachordner heraus ins StudyHub-Repo schreiben darf, den Repo-Pfad in ~/.claude/settings.json ergänzen: 

    {
  "permissions": {
    "additionalDirectories": [
      "/Users/DEIN-NAME/dev/school/StudyHub"
    ]
  }
}

    Ohne diesen Eintrag geht es auch — dann musst du Claude Code jedes Mal mit --add-dir starten.

  5. Prüfen, ob es erkannt wird

    Claude Code starten, / tippen — /studyhub-summary muss in der Liste auftauchen.

Lernziele

Sie bestimmen den Umfang der Zusammenfassung — nichts sonst.

Es gibt drei Wege, die Lernziele mitzugeben. Die erste vorhandene Quelle gewinnt, niedrigere Quellen dürfen ergänzen, aber den Umfang nicht überschreiben.

1. Direkt beim Aufruf — empfohlen

Weil die Lernziele sich bei jeder Prüfung ändern, ist das der einfachste Weg. Einfach hinter den Befehl schreiben:

/studyhub-summary Lernziele:
- Arbeitsvertrag definieren und Merkmale nennen
- Arbeitsvertrag vom Auftrag abgrenzen
- Kündigungsfristen berechnen

Prüfung am 14.09., 90 Minuten, Hilfsmittel: OR

2. Datei im Fachordner

Eine lernziele.md neben dem Material ablegen — sie wird bis drei Ebenen tief gefunden. Praktisch, wenn die Lehrperson die Lernziele ohnehin als Datei verteilt hat, und sie bleibt beim Material liegen.

3. Die Fallback-Datei

~/.claude/skills/studyhub-summary/LERNZIELE.md wird nur verwendet, wenn du nichts inline mitgegeben hast und keine Datei im Ordner liegt.

Format

Kein Template nötig, eine rohe Liste genügt. Je mehr Kontext, desto präziser das Ergebnis — besonders wertvoll sind Prüfungsform, Dauer, erlaubte Hilfsmittel und Hinweise der Lehrperson.

Jedes Lernziel wird nachweislich abgedeckt. Es wird erklärt, an einem Beispiel gezeigt, mit einer Übung geprüft und gelöst. Ein Lernziel, das nur in einer Überschrift vorkommt, gilt als nicht abgedeckt. Reicht das Material für ein Lernziel nicht aus, wird das gemeldet, bevor die Seite entsteht — nicht stillschweigend weggelassen.

Ablauf

Acht Phasen von den Rohdaten bis zur eingebundenen Seite.

  1. Phase 0 Preflight Ein Skript prüft Lernziele, Repo-Zugriff, Git-Zustand und erstellt ein Inventar des Ordners. Fehlt etwas Wesentliches, wird hier abgebrochen — mit dem konkreten Befehl zur Behebung.
  2. Phase 1 Analyse Material sichten und priorisieren, Fach, Schule und Thema bestimmen, Zielort im Repo festlegen, prüfen ob schon eine Seite dazu existiert. Daraus entsteht die Coverage-Map: Lernziel → Quelle → Konzepte → Beispiele → Übungen.
  3. Phase 2 Preflight-Bericht Kurze Übersicht des Erkannten: Bereich, Fach, Prüfung, Anzahl Lernziele, gefundene Quelldateien, Zielpfad. Rückfragen nur bei echten Blockern — nicht bei allem, was aus den Dateien ableitbar ist.
  4. Phase 3 Aufbau planen Gliederung festlegen, fachspezifisch angepasst. Mathematik braucht andere Didaktik als Recht oder Geschichte.
  5. Phase 4 Seite schreiben Eigenständige HTML-Seite mit eigenem CSS, ohne Frameworks. Deutsch (Schweiz), niemals ß. Wissen wird verdichtet, nicht weggelassen.
  6. Phase 5 Coverage-Gate Jedes Lernziel wird gegen Theorie, Beispiel, Übung und Lösung geprüft. Alles muss auf PASS stehen, sonst wird nachgebessert statt beschönigt.
  7. Phase 6 Integration und Validierung Datei an den richtigen Ort, Link in die Fächerübersicht, anschliessend automatische Prüfung durch ein Validierungsskript.
  8. Phase 7/8 Commit und Bericht Gezielter Commit nur der eigenen Dateien, danach ein knapper Abschlussbericht: was entstand, wie viele Lernziele abgedeckt sind, wie viele Übungen, was validiert wurde.

Aufbau

Wie das Skill intern organisiert ist — und warum so.

studyhub-summary/
├── SKILL.md                 Workflow in 8 Phasen — das Herzstück
├── config.example.md        Vorlage für die persönliche config.md
├── LERNZIELE.md             Fallback-Datei für die Lernziele
├── LERNZIELE.template.md    Leervorlage (dient der Template-Erkennung)
├── README.md
├── references/
│   ├── source-analysis.md       Material sichten, Prüfungsmodell, Coverage-Map
│   ├── summary-quality.md       Inhalt, Sprache, fachspezifische Didaktik
│   ├── exercises.md             Übungen auf 5 Niveaus, Lösungen, Simulation
│   └── studyhub-integration.md  Repo-Konventionen, Einbindung, Validierung
└── scripts/
    ├── preflight.sh         Lernziele, Zugriff, Git-Zustand, Materialinventar
    └── validate.sh          HTML, Anker, Sprache, Lecks, Index-Verlinkung

Warum die Aufteilung in references/

SKILL.md bleibt bewusst kurz und beschreibt nur den Ablauf. Die langen inhaltlichen Vorgaben — wie eine gute Übung aussieht, wie Mathematik anders behandelt wird als Geschichte — stehen in eigenen Dateien und werden nur dann gelesen, wenn sie in der jeweiligen Phase gebraucht werden. Das hält den Arbeitsspeicher schlank und die Anweisungen trotzdem ausführlich.

Warum Skripte

Die beiden Shell-Skripte machen genau das, was ein Sprachmodell unzuverlässig macht und ein Skript deterministisch: zählen, vergleichen, prüfen. Ob ein ß in der Datei steht, ob ein Anker ins Leere zeigt oder ob der Link in der Übersicht wirklich existiert, ist nichts, was man schätzen sollte.

Was preflight.sh prüft
  • Sind Lernziele vorhanden — und aus welcher der drei Quellen?
  • Erkennt, wenn die Fallback-Datei noch das unveränderte Template ist
  • Ist das StudyHub-Repo les- und schreibbar? Sonst: exakter Befehl zur Behebung
  • Git-Zustand: Branch, laufender Merge oder Rebase, Detached HEAD
  • Fremde uncommittete Änderungen werden aufgelistet und geschützt
  • Inventar des Ordners, ohne node_modules, Caches und Build-Output
  • Hebt prüfungsrelevante Dateien hervor, damit sie zuerst gelesen werden
Was validate.sh prüft
  • Ablageort und Dateiname entsprechen der Konvention
  • Kein ß, keine unnötige Umschreibung von Umlauten
  • Doctype, Charset, Viewport, Titel, lang-Attribut
  • Tag-Balance und doppelte IDs
  • Tote Sprungmarken und ins Leere zeigende relative Verweise
  • Übrig gebliebene Platzhalter oder TODO-Reste
  • Versehentlich geleakte lokale Dateipfade
  • Übungen und Lösungen sind tatsächlich vorhanden
  • Externe Abhängigkeiten — das Repo soll ohne Build und ohne Framework laufen
  • Syntaxprüfung des Inline-JavaScripts
  • Der Link in der Fächerübersicht existiert, und alle Links dort zeigen auf echte Dateien

Qualitätsregeln

Die Vorgaben, an denen sich jede erzeugte Seite messen lassen muss.

Der Massstab

Jede Seite muss diese Frage mit Ja beantworten: „Wenn ich alles auf dieser Seite verstehe und lösen kann — bin ich nach den gelieferten Lernzielen optimal auf die Prüfung vorbereitet?"

Übungen auf fünf Niveaus

Übungen sind Pflicht, keine Dekoration. Die Mehrheit darf ausdrücklich nicht blosses Abfragen sein.

LevelNameWas geprüft wird
1GrundlagenDefinitionen und Grundverfahren
2AnwendungWissen auf normale Situationen anwenden
3Schwierige AnwendungMehrere Konzepte kombinieren
4TransferWissen in neuer, ungewohnter Situation einsetzen
5PrüfungssimulationRealistisch schwer, Methode nicht offensichtlich

Vorhandene Aufgaben werden nicht einfach abgeschrieben, sondern zu Varianten umgebaut, die dieselbe Kompetenz prüfen — teils bewusst mit Fallen wie überflüssigen Angaben, leicht veränderten Bedingungen oder einer fehlerhaften Lösung, die gefunden werden soll.

Lösungen erklären, nicht nur nennen

Jede Lösung sagt, welches Konzept geprüft wird, wie man den Ansatz erkennt, wie der Weg aussieht, was herauskommt — und wo der typische Irrweg liegt.

Sprache

Deutsch (Schweiz): niemals ß, immer ss. Umlaute bleiben Umlaute. Fremdsprachliche Lerninhalte bleiben in ihrer Sprache — ein englischer Beispielsatz bleibt englisch, die Erklärung drumherum ist deutsch.

Nicht überzusammenfassen

Der häufigste Fehler wäre, aus 100 Seiten Material zwei Seiten HTML zu machen. Redundanz wird verdichtet, Wissen nicht. Definitionen, Ausnahmen, Verfahren und Beispiele bleiben drin.

Keine erfundenen Fakten

Gesetzesartikel, Formeln, historische Daten, Befehle, Prüfungsregeln und Vorgaben der Lehrperson werden nie erfunden. Widersprechen sich Quellen und lässt sich das nicht auflösen, wird nachgefragt statt geraten.

Sicherheit

Was das Skill niemals tut.

Standardmässig wird committet, aber nicht gepusht. Nichts landet auf der Website, bevor du selbst git push ausführst. Wer das anders will, stellt in config.md auf Modus C um.

  • Es werden nur die selbst erstellten Dateien gestaged — gezielt per git add <pfad>, nie git add -A.
  • Fremde uncommittete Änderungen bleiben unangetastet und werden im Preflight aufgelistet.
  • Kein git reset --hard, kein git clean -fd, kein Force-Push.
  • Läuft ein Merge oder Rebase, oder ist HEAD detached, wird abgebrochen und nachgefragt.
  • Eine bestehende Zusammenfassung wird nie überschrieben, nur weil der Name ähnlich ist.
  • Lokale Dateipfade, Benutzernamen und private Dateinamen gelangen nicht in die öffentliche Seite — validate.sh prüft das eigens.

Wenn schon eine Seite zum Thema existiert

Dann wird sie vollständig gelesen, mit den aktuellen Lernzielen und dem aktuellen Material abgeglichen und gezielt verbessert — nicht blind neu erzeugt. Gute vorhandene Inhalte bleiben erhalten. Ist unklar, ob es sich um ein Update oder eine eigene neue Seite handelt, wird gefragt.

Wenn etwas klemmt

Die häufigsten Fälle und was dann passiert.

/studyhub-summary erscheint nicht in der Liste

Prüfen, ob der Ordner wirklich unter ~/.claude/skills/studyhub-summary/ liegt und eine SKILL.md mit Frontmatter enthält. Danach Claude Code neu starten. Skills werden beim Start eingelesen.

Es findet das StudyHub-Repo nicht

Der Pfad in config.md stimmt nicht mit deinem tatsächlichen Klon überein. Die Skripte lesen die erste alleinstehende Pfadzeile in dieser Datei. Alternativ per Umgebungsvariable, die Vorrang hat: 

export STUDYHUB_REPO="$HOME/dev/school/StudyHub"
Kein Schreibzugriff aufs Repo

Claude Code darf standardmässig nur im Startordner arbeiten. Entweder den Repo-Pfad dauerhaft in ~/.claude/settings.json unter additionalDirectories eintragen, oder pro Sitzung: 

claude --add-dir ~/dev/school/StudyHub

Das Skill erkennt den fehlenden Zugriff selbst und nennt dir den exakten Befehl.

Es sagt, es fehle Material für ein Lernziel

Das ist Absicht und kein Fehler. Statt ein Lernziel mit erfundenem Inhalt zu füllen, wird konkret benannt, was fehlt. Ergänze die Unterlagen im Ordner oder beantworte die Rückfrage — danach läuft es weiter.

Die Seite ist online nicht sichtbar

Wahrscheinlich fehlt der Push. Das Skill committet standardmässig nur lokal: 

cd ~/dev/school/StudyHub
git log --oneline -1
git push

Danach deployt Netlify automatisch, das dauert etwa eine Minute.

Kann ich das auch für ein anderes Fach oder Modul nutzen?

Ja. Das Skill ist bewusst nicht auf ein einzelnes Fach zugeschnitten und passt seine Didaktik an — Mathematik, Physik, Chemie, Wirtschaft & Recht, Geschichte & Politik, Sprachen sowie IT-Module. Existiert für dein Fach noch keine Karte in der Übersicht, wird sie mitsamt Ordnerstruktur angelegt.

Der vollständige Quelltext des Skills liegt im Repo unter claude-skill/studyhub-summary/.
